# 执行纪律与工具规则

## 1. 先学习，再实现

关键能力开始前固定节奏：`问题/原理 → owning Spec → 方案取舍 → 实现 → 真实验证 → 实战档案`。禁止长时间后台批量写完后只汇报“完成”。

## 2. SDD 与最小变更

实现必须服从已冻结 Spec。现实证明 Spec 不成立时，STOP 并先 Amendment；不能让代码偷偷成为新规范。目录允许演进，但改变部署单元、Bounded Context、跨域契约、共享 package 或数据 ownership 必须先 Review。

## 3. 本地工程工具路由

```text
Repomix   = Context Plane：最小充分范围的批量仓库上下文
CodeGraph = Structure Plane：调用链、ownership、blast radius
Local Dev = Execution Plane：当前磁盘、批量读写、Git、test/build
Playwright= Reality Plane：真实 Site / Browser 行为
```

仓库理解/修改默认先对最小相关目录做 Repomix；需要结构证明时进入 CodeGraph；当前磁盘和实际执行以 Local Dev 为准；真实 Site/UI 才用 Playwright。纯 Git/test/command 机械动作可以直接 Local Dev。

## 4. 高吞吐

禁止 `read A → read B → edit A → edit B` 的 per-file loop。多文件先批量理解，再一次 transform，再一次 `diff/check + targeted gate + status`。长任务一次启动、合理读取；非幂等 mutation timeout/UNKNOWN 时先恢复权威状态，禁止盲重试。

## 5. RAG 学习硬门

- Chunking、Embedding、Hybrid Retrieval、RRF、Rerank、Evidence、Context、Generation、Eval 逐层实现和观察。
- 核心 RAG Pipeline 不由 LangChain/LlamaIndex 黑盒化。
- Retrieval 未通过 benchmark 前，不用 LLM 生成掩盖检索缺陷。
- 真实参数由 Mac+iPhone 实验决定，不预填漂亮数字。

## 6. 沟通确认门

关键实现单元完成机械验证后，必须先向用户讲清“做了什么、为什么、代码边界、真实问题、取舍和证据”，进入讨论与质疑。机械 Gate PASS 只表示实现候选可评审，不自动等于阶段 PASS。

固定顺序：`实现候选 → 机械验证 → 讲解/讨论 → 用户确认 → 正式 closeout / 文档沉淀 / 阶段推进`。未经用户确认，禁止提前把 CURRENT 推到下一阶段、把阶段标 PASS/FROZEN，或把实战文档中的结论当成已共同确认。

## 7. 阶段闭环

阶段只有同时满足 Spec、Implementation、Verification、用户确认与实战档案写回才算 closeout。
## 8. 学习沟通优先级

用户是资深前端开发工程师。讲解与讨论优先分配给 RAG 核心能力和用户相对不熟悉的后端技术栈；常规前端、Monorepo、TypeScript、Git 与一般工程杂项默认压缩处理。只有这些杂项直接影响 RAG 正确性、后端架构或形成有价值的真实排障证据时，才展开并合并记录，不能挤占 RAG 主线。

## 9. 专业术语首次出现规则

RAG 与后端技术域的专业术语第一次出现时，必须先说明中文含义、它在当前链路解决什么问题，并给一个当前项目例子，再继续使用英文简称。不能因为用户是资深前端工程师，就默认其已掌握 RAG/后端专有词汇。前端与通用工程术语可压缩。

## 10. 文件级说明与 Commit 可读性

每次新增或关键修改文件时，必须让用户不通读实现也能快速理解“这个文件为什么存在、负责什么、属于哪一层、关键边界是什么”。可写注释的源码/脚本/YAML 使用文件头注释；Markdown 在标题后写文件职责/当前作用；JSON、lockfile 等不支持注释的格式不得为了说明而破坏语法，改由对应 owner 文档与 commit file summary 逐文件说明。

每个 commit 除简洁主题外，还必须提供按文件的变更说明：列出新增/关键修改文件及其职责、本次具体变化和必要的设计原因。禁止只写一个笼统 commit subject，让用户只能通过完整 diff 猜本次提交做了什么。
