# 历史问题与防回归清单

这些不是待办，而是项目已经出现过或明确识别的高成本反模式。

## 1. 摆钟式架构纠偏

症状：用户提出 DDD 就全面 DDD，提醒 SDD 又试图推翻 DDD。
规则：新问题先判断是补充、纠偏、冲突还是新需求，再修改整体设计。当前结论是 SDD 治理 + DDD 建模 + Capability Spec + Verification，四者同时成立。

## 2. 过早 Freeze

症状：薄 Spec、大量文件统一改状态就宣称冻结。
规则：分层冻结；只有边界/契约/不变量有明确验证映射才 Freeze，实验参数保持 REVIEWED/待实测。

## 3. 把技术组件伪装成 Domain

症状：Retrieval、Conversation、Platform 等按目录就称 Bounded Context。
规则：当前只有 Knowledge Management、Grounded Answering、Quality & Evaluation 三个 Context；技术能力归 owning Context，Infrastructure 不是 Domain。

## 4. 只实现，不教学

症状：后台一次写大量代码，用户只能看到结果。
规则：实现过程即学习过程；关键能力实现前先讲问题、原理和设计，再小步实现与验证。

## 5. 只记录最终漂亮方案

症状：面试档案没有真实失败、排障和取舍。
规则：实战档案必须记录初始假设、失败现象、根因、修复、数据和 Git evidence；未验证猜测不得包装成经历。

## 6. 换 Chat 重新探索

规则：先读公共上下文和 REQUIRED_CONTEXT；没有新的 regression evidence，不重开已经 FROZEN/PASS 的设计结论。

## 7. 用旧 TypeScript / Node 模块心智套当前生态

症状：P0 初始把 `moduleResolution: Node` 当成稳定默认，TypeScript 7 已移除对应 Node10 解析；随后 CommonJS 又与 NestJS 12 ESM 包边界冲突。
规则：工具链版本先机械读取 Registry/engine；当前 P0 基线采用 Node `>=20` + TypeScript NodeNext/ESM，不为兼容旧习惯强制退回 CommonJS。

## 8. 把临时 Registry 网络抖动当依赖失败

症状：安装 Fastify 依赖时 npm Registry 出现多次 `ECONNRESET`。
规则：先看包管理器最终状态和 lockfile；可恢复 GET 由 pnpm 正常重试不升级为 blocker。只有最终 install UNKNOWN/FAIL 才进入网络排障。

## 9. 先封板、后沟通

症状：P0 实现候选和机械 Gate 完成后，后台直接更新 CURRENT、实战档案和阶段文档，宣布 P0 PASS 并推进 P1，用户还没有机会理解和质疑“到底做了什么”。
规则：实现过程本身就是学习过程。固定采用 `实现候选 → 机械验证 → 讲解/讨论 → 用户确认 → closeout/沉淀/阶段推进`。任何自动 closeout 都不得跨过用户确认门。`696482b` 作为这次过早 closeout 的历史证据，不作为 P0 用户验收依据。
