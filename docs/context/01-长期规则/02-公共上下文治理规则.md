# 公共上下文治理规则

> 目标：让项目在多 Chat、长周期实现中保持连续，同时避免公共上下文膨胀成第二套 Spec。

## 四层 ownership

- `01-长期规则`：所有未来执行者必须知道的铁律，低频变化。
- `02-当前接力/CURRENT.md`：唯一当前事实入口，高频覆盖更新。
- `03-执行知识库`：可复用的基础动作、阶段流程与恢复方法。
- `90-历史记录`：只用于追溯过去证据，默认不加载。

## 写回判断

```text
所有未来 Chat 必须知道？        → 01-长期规则
下一 Chat 接着做必须知道？       → CURRENT
以后遇到同类动作还能复用？       → 03-执行知识库
正式设计/Contract/Ownership 改了？→ docs/specs
真实实现与面试过程要保留？       → ai-agent-platform 实战档案
只是本轮日志/旧截图/事故证据？    → 90-历史记录
```

## Round Closeout 六问

关键实现单元先经过“实现候选 → 机械验证 → 用户讲解/讨论 → 用户确认”门禁；确认前 CURRENT 只能记录候选与待评审状态，不得提前写成阶段 PASS 或推进下一 Gate。

每完成一个已经允许 closeout 的设计/实现/实验 Round，进入下一 Round 前必须检查：

1. `CURRENT` 的 stage/checkpoint/blocker/next action 是否变化？
2. 是否产生新的稳定执行或恢复经验，应进入 Runbook？
3. 是否出现 Spec 与现实不一致，需要 Amendment？
4. Verification / Eval evidence 是否已经落盘或可机械回读？
5. `proflow-rag-engineering-practice` 是否记录了真实过程、问题、根因、取舍与面试证据？
6. 是否存在只应该进入历史的原始证据？

没有变化可以明确跳过；未验证猜测、一次性 PID、重复命令输出不得污染稳定上下文。

## REQUIRED_CONTEXT 硬规则

CURRENT 遇到已知阶段/能力时必须列出 `REQUIRED_CONTEXT`。接手者先读指定 Runbook/Spec，再诊断；禁止因换 Chat 重新探索已裁决问题。只有新的机械事实与文档冲突时，才更新 owner 文档。

## 上下文验收

上下文机制调整后必须做一次“失忆接管检查”：只给 `README + 长期规则 + CURRENT + REQUIRED_CONTEXT`，应能回答当前目标、下一步、真源、禁止重做项、失败恢复入口。答不出来即为 `CONTEXT_MIGRATION_GAP`。
