# Knowledge｜解析与结构化分块 Spec

状态：FROZEN_V0_2026-09-03

## 1. 目标
Chunking 的目标不是把文件机械切成固定 token，而是保留足够完整的工程语义，让 Retriever 能召回“一个能被理解和引用的知识单元”。

## 2. 文档 Parser/Chunker
Markdown 优先保留标题层级、章节、段落、列表和代码块关系。Chunk metadata 至少包含 heading path、文件路径和起止行。普通段落不应因为达到固定长度而无条件从句子中间切断。

## 3. 源码 Parser/Chunker
源码优先以 class、function、method、interface/type、模块级常量或其他可识别结构作为边界。Chunk 应保留 symbol/name、parent symbol（若有）、语言、文件路径和行范围。不能依赖某个私有 CodeGraph 工具；结构解析必须由 `proflow-rag` 自身实现或使用可随项目安装的解析库。

## 4. 测试 Parser/Chunker
测试优先按 `describe/context` 与 `it/test` 语义切分，保留测试标题、关键 setup 和 assertion。目标是让“某能力是否被验证”能直接召回对应完整测试意图，而不是半截代码。

## 5. 超大结构单元
如果一个函数/章节远超 Embedding 或 Context 的合理大小，允许在父结构内部二次分块并保留 parent metadata 与有限 overlap；所有子块仍必须回到原始行范围。

## 6. Fixed-size Baseline
保留一个固定长度 + overlap 的 baseline，仅用于 Eval 比较。它不是 V0 默认生产 Chunker，也不能因为实现简单而替代结构化策略。

## 7. 标准 Chunk 契约
`chunk_id, snapshot_id, document_id, source_type(doc|code|test), file_path, start_line, end_line, heading?, symbol?, parent_ref?, content, content_hash, metadata`。

## 8. 质量约束
- 不产生空 Chunk、仅标点 Chunk 或重复内容 Chunk。
- 行号以索引 commit 的原始文件为准。
- Chunk text 允许加入最少的标题/symbol 上下文，但不得改变原始事实。
- parser/chunker 版本写入 Snapshot 构建配置。

## 9. 验收
从随机抽样 Chunk 能反查 GitHub 原文件并验证行范围；典型 README 章节、TypeScript 函数和测试用例不被无意义切碎；结构化 Chunk 在 Eval 上与 fixed-size baseline 有可比较结果。
