# ProFlow RAG｜DDD 领域地图

状态：FROZEN_V0_2026-09-03

## 1. 领域划分原则
一级目录不按 Embedding、Reranker、Database 这类技术组件切割，而按业务责任与生命周期切割。一个领域必须能回答“它为什么存在、拥有哪类事实、输入和输出是什么、失败由谁承担”。

## 2. Knowledge｜知识构建域（核心域）
职责：把 ProFlow GitHub `main` 的某个确定 commit 构造成可检索、可验证、可激活的 Knowledge Snapshot。
拥有：RepositorySnapshot、CorpusDocument、Chunk、EmbeddingBinding、KnowledgeSnapshot、IngestionRun。
不负责：解释用户问题、生成答案、管理会话。

## 3. Retrieval｜检索域（核心域）
职责：给定 RetrievalQuery，在 Active Knowledge Snapshot 中找到最相关、最可信的 ProFlow 证据，输出 EvidenceSet。
拥有：RetrievalQuery、Candidate、FusionResult、RerankResult、Evidence、EvidenceSet。
不负责：生成最终自然语言答案，也不负责构建或激活知识索引。

## 4. Conversation｜会话问答域（核心域）
职责：管理一次匿名多轮问答的语义上下文、FAST/THINK 路由、Context Budget、生成与流式回答。
拥有：Conversation、Turn、StandaloneQuery、ContextPlan、Answer、SourceCitation。
不拥有：知识快照生命周期、检索索引、数据库连接细节。

## 5. Evaluation｜评估审计域（支撑域）
职责：记录真实 RAG 执行轨迹、用户反馈、基准样本与回归结果，回答“系统效果如何、问题发生在哪个阶段”。
拥有：RAGTrace、Feedback、EvalCase、EvalRun、MetricResult。
不参与在线答案业务裁决，不允许为了统计方便改变核心领域语义。

## 6. Platform｜平台支撑域（支撑域）
职责：提供 PostgreSQL、Model Gateway、配置、安全、Dev Tunnel 生命周期、调度、健康检查等运行能力。
核心领域只依赖 Platform 暴露的稳定 Port/Contract，不得直接依赖 LAN 地址、数据库连接字符串或进程管理实现。

## 7. Delivery｜交付界面（接口上下文）
职责：HTTP API 与 ChatGPT Sites 的请求/响应适配、SSE 展示、匿名 Visitor 标识传递、Sources 与极简反馈 UI。
Delivery 不拥有 RAG 核心业务规则；换成 CLI、MCP 或其他 Web 前端时，Knowledge/Retrieval/Conversation 不应被迫重写。

## 8. Context Map
```text
Knowledge ──ActiveKnowledgeSnapshot──> Retrieval
Retrieval ──EvidenceSet──────────────> Conversation
Conversation ──RAG execution events──> Evaluation
Delivery ──commands/queries──────────> Conversation
Platform ──ports/adapters────────────> 所有需要基础设施的领域
```

## 9. 依赖方向不变量
- Conversation 可以调用 Retrieval，但 Retrieval 不反向依赖 Conversation。
- Retrieval 可以读取 Knowledge 发布的 Active Snapshot 契约，但不能操纵 Snapshot 激活。
- Knowledge 不知道 Chat、Site、Visitor 或 Prompt。
- Evaluation 观察其他领域的事实，不成为它们运行成功的强依赖；审计写入失败不能导致已经生成的用户回答被伪造成失败。
- Delivery 不直接查询 PostgreSQL 的 RAG 表，也不直接调用 iPhone 模型。
